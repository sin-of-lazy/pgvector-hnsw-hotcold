# 优化方向

我们做三个方向的优化，分别是查询速度、构建速度、内存占用。

查询速度方面做两点优化：一是搜索候选队列优化，pgvector HNSW 的 `HnswSearchLayer()` 用的是二叉堆，**热点是堆操作和距离计算交替进行**，可以做批量预取；二是 `ef_search` 动态调整，当前 `ef_search` 是静态 GUC，可以在 C 层根据查询的 `limit` 值自动推算最小合理 ef。

构建速度方面做两点优化：一是并行 build 的锁粒度优化，pgvector 的 `CREATE INDEX` 走 PG 的并行 worker 框架，但 **HNSW 插入时的图连接阶段存在全局锁竞争**，核心在 `HnswInsertElement()` 里对上层节点邻居列表的加锁，改进方向是把邻居列表的锁从 page-level 拆成 **per-node 细粒度锁**（类似论文里的 lock-free HNSW 思路），但在 PG 的 buffer 框架内实现需要借助 `LWLock`；二是向量预加载与 I/O 批量化，build 时顺序扫描堆表，可以在 `HnswBuildCallback` 里用 `PrefetchBuffer` 预读后续 tuple。

内存占用方面做两点优化：一是邻居列表的存储压缩，当前每个节点的邻居存的是完整的 ItemPointerData（6 字节 ctid）+ 距离（4字节 float），对于千万级数据，可以把距离从 float32 降为 float16 存储，查询时再提升；二是基于Buffer Pool的HNSW冷热分层优化，具体为把 HNSW 的“常访问上层节点”当作**热数据**优先放内存，把“访问少的底层节点”当作**冷数据**按需从 Buffer Pool 读取。
