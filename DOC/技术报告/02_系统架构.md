# 第 2 章：系统架构

## 2.1 pgvector 在 PostgreSQL 中的位置

pgvector 不是独立数据库，而是 **PostgreSQL 扩展**，通过 Index Access Method (AM) 接口与 PG 核心协作。

### 2.1.1 整体调用链

```
用户 SQL
  ↓ PostgreSQL Parser
  ↓ Planner / Optimizer
  ↓ 识别 ORDER BY embedding <-> query LIMIT k
  ↓ 生成 Index Scan 计划
  ↓ Executor 调用 IndexAmRoutine 回调
  ↓ pgvector 的 hnswgettuple()
  ↓ HnswSearchLayer 在图中搜索
  ↓ 返回 heap TID 给 Executor
  ↓ Executor 根据 TID 回表（MVCC 可见性判断）
  ↓ 返回结果给客户端
```

**关键点**：

- pgvector 只负责**索引数据结构 + 搜索逻辑**
- PostgreSQL 负责 **SQL 解析、MVCC、Buffer Pool、WAL、锁**
- 向量数据同时存在 heap table 和 index 两处（index 存 float 向量本体，用于距离计算）

### 2.1.2 Index AM 回调表

pgvector 通过 `hnswhandler()` 注册给 PostgreSQL：

| PostgreSQL 事件 | pgvector HNSW 函数 | 所在文件 |
|---|---|---|
| 创建索引 | `hnswbuild` | `src/hnswbuild.c` |
| 插入索引项 | `hnswinsert` | `src/hnswinsert.c` |
| 开始扫描 | `hnswbeginscan` | `src/hnswscan.c` |
| 重新扫描 | `hnswrescan` | `src/hnswscan.c` |
| 获取下一条 | `hnswgettuple` | `src/hnswscan.c` |
| 结束扫描 | `hnswendscan` | `src/hnswscan.c` |
| VACUUM 删除 | `hnswbulkdelete` | `src/hnswvacuum.c` |
| VACUUM 清理 | `hnswvacuumcleanup` | `src/hnswvacuum.c` |
| 估算代价 | `hnswcostestimate` | `src/hnsw.c` |
| 解析索引选项 | `hnswoptions` | `src/hnsw.c` |

我们的优化主要集中在 **scan 路径**（`hnswscan.c` + `hnswutils.c`）。

## 2.3 HNSW 磁盘格式

### 2.3.1 Page 类型

- **Meta Page (block 0)**：存 `m`、`ef_construction`、`entryBlkno`、`entryOffno`
- **Element Pages**：存单个向量节点（向量本体 + heap TID 数组 + level + neighbor 指针）
- **Neighbor Pages**：存某层的邻居列表（`ItemPointerData` 数组）

### 2.3.2 元素结构

```c
typedef struct HnswElementTupleData {
    uint8   type;                      // HNSW_ELEMENT_TUPLE_TYPE
    uint8   level;                     // 最高层数
    uint8   deleted;                   // VACUUM 标记
    uint8   version;                   // 防止并发问题
    ItemPointerData heaptids[10];      // 回表 TID（支持 HOT 更新）
    ItemPointerData neighbortid;       // 指向 neighbor tuple
    Vector  data;                      // 向量本体（变长）
} HnswElementTupleData;
```

### 2.3.3 邻居列表结构

```c
typedef struct HnswNeighborTupleData {
    uint8   type;                      // HNSW_NEIGHBOR_TUPLE_TYPE
    uint8   version;
    uint16  count;                     // 当前层邻居数
    ItemPointerData indextids[];       // 邻居元素的 (blkno, offno)
} HnswNeighborTupleData;
```

**关键**：邻居列表只存 `ItemPointerData`（6 字节 = 4B blkno + 2B offno），不存距离。Phase 1 的 prefetch 就是根据这些 `blkno` 提前发起 I/O。

## 2.4 查询流程详解

假设执行：

```sql
SELECT id FROM items ORDER BY embedding <-> '[0.1,0.2,...]' LIMIT 10;
```

### 2.4.1 Executor 调用链

```
hnswbeginscan()          分配 HnswScanOpaque，设置 support functions
  ↓
hnswrescan()             接收查询向量，初始化 visited 哈希表
  ↓
hnswgettuple()           第一次调用时触发 GetScanItems()
  ↓ GetScanItems()       从入口点开始逐层下降
    ├─ HnswEntryCandidate()  加载入口点
    ├─ for lc = entryLevel..1:
    │    HnswSearchLayer(..., ef=1, lc)  // 高层用 ef=1 贪心导航
    └─ HnswSearchLayer(..., ef=hnsw_ef_search, lc=0)  // 第 0 层 beam search
  ↓
HnswSearchLayer()        核心搜索循环（Algorithm 2）
  ├─ 从候选堆 C 取最近候选
  ├─ HnswLoadUnvisitedFromDisk()  读邻居列表 ← Phase 1 在这里加 prefetch
  ├─ for each unvisited neighbor:
  │    HnswLoadElementImpl()      加载邻居元素
  │    计算距离
  │    更新 C / W 堆
  └─ 返回 Top-ef 候选
  ↓
hnswgettuple()           逐个返回候选的 heap TID
  ↓
Executor 回表            根据 TID 访问 heap tuple，MVCC 可见性判断
  ↓
返回结果
```

### 2.4.2 Phase 1 优化插入点

在 `HnswSearchLayer` 的循环中：

```c
// 原始逻辑（官方）
HnswLoadUnvisitedFromDisk(cElement, unvisited, &unvisitedLength, v, index, m, lm, lc);

// Phase 1 新增（紧随其后）
if (!inMemory && hnsw_hot_cold_enabled && hnsw_prefetch_neighbors > 0) {
    int prefetchCount = ...;
    for (int pi = 0; pi < prefetchCount; pi++) {
        BlockNumber blk = ItemPointerGetBlockNumber(&unvisited[pi].indextid);
        if (blk != InvalidBlockNumber)
            PrefetchBuffer(index, MAIN_FORKNUM, blk);
    }
}

// 继续原始逻辑：逐个加载邻居
for (int i = 0; i < unvisitedLength; i++) {
    HnswLoadElementImpl(...);  // 这时大概率已经在 buffer pool 里了
    ...
}
```

**为什么有效**：

- `unvisited[]` 包含即将访问的所有邻居 TID
- `PrefetchBuffer` 是异步提示，立即返回，PG 后台启动 I/O
- 后续 `HnswLoadElementImpl` 访问时，页面大概率已经在 buffer pool 里
- 把原本串行的 "miss → block → load → continue" 转成了并发的 "prefetch all → load all（几乎全命中）"

## 2.5 Buffer Pool 与 PrefetchBuffer 机制

### 2.5.1 PostgreSQL Buffer Pool

- 共享内存区域，大小由 `shared_buffers` 控制（默认 128MB，生产建议数 GB）
- 按 8KB 页管理，LRU 淘汰策略
- `BufferAccessStrategy` 允许不同操作使用不同策略（如 bulk scan 用 ring buffer）

### 2.5.2 PrefetchBuffer API

```c
void PrefetchBuffer(Relation reln, ForkNumber forkNum, BlockNumber blockNum);
```

- **功能**：告诉 PG "我即将访问这个 block，如果不在 buffer pool 里请提前加载"
- **异步**：立即返回，不阻塞调用者
- **幂等**：如果页面已在 buffer pool 里，什么也不做（零开销）
- **无保证**：只是 hint，PG 可能因内存压力或 I/O 繁忙而忽略

**适用场景**：

- 已知即将访问的页面序列（如 index scan 的邻居列表）
- 访问模式是顺序或可预测的
- 内存充足，预取不会导致 buffer pool 污染
