# 优化方向

本文档记录当前项目后续要实现的 pgvector HNSW 优化路线。当前项目已经融合到 pgvector 0.8.4，后续优化应尽量保持低侵入、可灰度、可 benchmark 验证。

我们只保留四个阶段：

1. HNSW 查询路径 GUC + neighbor prefetch + hot layer 策略
2. `ef_search` 动态/半动态调优
3. HNSW 构建期 I/O 优化
4. 并行 build 锁粒度优化

暂不纳入当前实现范围的方向已经删除，包括：邻居距离 float16 压缩、复杂自建 hot cache、VACUUM 路径改动。

---

## Phase 1：HNSW 查询路径 GUC + neighbor prefetch + hot layer 策略

### 目标

第一阶段目标是做一个低风险、可验证的查询路径优化原型。

核心思想：HNSW 查询时会从入口点逐层下降，并在第 0 层大量访问邻居节点。邻居节点通常分布在不同 index page 上，容易产生随机访问。我们可以基于 HNSW 的邻居访问模式，在真正加载邻居元素前，对即将访问的 neighbor page 发起 `PrefetchBuffer`，让 PostgreSQL Buffer Pool 提前准备相关页面。

这不是重新实现一套缓存，而是利用 PostgreSQL 原生 Buffer Pool 做访问策略优化。

### 计划新增 GUC

```text
hnsw.hot_cold_enabled
hnsw.hot_layer
hnsw.hot_max_bytes
hnsw.prefetch_neighbors
```

第一版中，`hnsw.hot_max_bytes` 可以先作为预留参数，不急着实现复杂热缓存。真正优先落地的是：

```text
hnsw.hot_cold_enabled
hnsw.hot_layer
hnsw.prefetch_neighbors
```

### 主要修改文件

```text
src/hnsw.h
src/hnsw.c
src/hnswscan.c
src/hnswutils.c
test/hot_cold/*
```

### 文件作用

`src/hnsw.h`：

- 声明新的 GUC 全局变量
- 如有需要，扩展 HNSW scan 状态

`src/hnsw.c`：

- 在 `HnswInit()` 中注册新的 GUC 参数
- 设置默认值和合法范围

`src/hnswscan.c`：

- HNSW 查询扫描入口
- 如有需要，在单次 scan 开始时读取 GUC 快照

`src/hnswutils.c`：

- HNSW 搜索核心逻辑
- 推荐在 `HnswLoadUnvisitedFromDisk()` 附近实现 neighbor page prefetch
- 依据 `lc >= hnsw_hot_layer` 决定是否更积极预取

`test/hot_cold/*`：

- 验证 GUC 存在
- 验证查询仍走 HNSW Index Scan
- 验证 Recall@10 不明显下降
- 用 `EXPLAIN (ANALYZE, BUFFERS)` 对比 buffer 行为

### 验证指标

```text
Recall@10 >= 0.95
hot/cold on/off 查询结果一致或近似一致
EXPLAIN 中仍使用 HNSW Index Scan
观察 shared hit / shared read / Execution Time 变化
```

### 必要性

这个阶段最贴近 RAG / AI Agent 在线检索场景，能体现 AI Infra 中常见的低延迟、高召回、Buffer Pool 行为优化问题。

### 可行性

高。

原因：

- 不改变磁盘格式
- 不改变 HNSW 图结构
- 不改变 VACUUM / INSERT 逻辑
- 可以用 GUC 开关灰度
- 可以直接 benchmark 验证

## Phase 2：`ef_search` 动态/半动态调优

### 目标

当前 `hnsw.ef_search` 是静态 GUC。它越大，召回率通常越高，但查询代价也越高。第二阶段目标是探索更智能的 `ef_search` 调整策略，在召回率和延迟之间取得更好的平衡。

### 重要约束

不能简单假设 HNSW C 层一定能直接拿到 SQL 的 `LIMIT` 值。PostgreSQL 的 Index AM 扫描接口通常是 Executor 按需向索引要下一条 tuple，HNSW 查询函数并不天然知道上层完整查询语义。

因此，第一版不建议直接实现“根据 LIMIT 自动推算 ef_search”。更稳的方向是半动态策略。

### 可选方案

方案 A：新增自动模式 GUC

```text
hnsw.ef_search_auto = off/on
hnsw.ef_search_multiplier = 4
```

方案 B：基于 iterative scan 行为调整

```text
如果 discarded 候选较多，说明初始 ef 可能不足
如果 scan 多次扩展，说明 ef_search 可以适当提高
```

方案 C：基于用户显式参数

```text
用户仍设置基础 ef_search
系统根据过滤情况或扫描阶段做有限扩展
```

### 主要修改文件

```text
src/hnsw.h
src/hnsw.c
src/hnswscan.c
src/hnswutils.c
```

### 文件作用

`src/hnsw.c`：

- 注册新的 ef 调优相关 GUC

`src/hnswscan.c`：

- 管理 scan 批次
- 当前已有 iterative scan 逻辑，可作为动态扩展依据

`src/hnswutils.c`：

- `HnswSearchLayer()` 接收或使用最终 ef 值

### 验证指标

```text
Recall@10
平均延迟
P95 / P99 延迟
不同 LIMIT / 不同过滤条件下的表现
```

### 必要性

中高。

RAG / Agent 查询通常是 Top-K 检索。`ef_search` 对召回和延迟影响很大，因此调优有实际意义。

### 可行性

中。

原因：

- PostgreSQL Index AM 不一定直接暴露 LIMIT
- 需要避免影响现有 iterative scan 语义
- 需要大量 benchmark 支撑

## Phase 3：HNSW 构建期 I/O 优化

### 目标

第三阶段关注 `CREATE INDEX ... USING hnsw` 的构建性能，尤其是大规模向量数据构建 HNSW 索引时的 I/O 行为和构建耗时。

HNSW build 阶段需要扫描 heap 表、构建图、写入 index page。对于大数据量，构建耗时和 I/O 抖动会影响工程可用性。

### 优化思路

优先做观测，再决定是否加入预取。

可探索方向：

```text
1. 观测 HNSW build 阶段耗时分布
2. 分析 heap scan、图连接、index page 写入各自占比
3. 在明确存在 I/O 等待时，再考虑预取策略
4. 尽量复用 PostgreSQL 自身的 table scan / buffer access strategy
```

### 主要修改文件

```text
src/hnswbuild.c
src/hnswutils.c
```

### 文件作用

`src/hnswbuild.c`：

- HNSW 索引构建入口
- 处理 `CREATE INDEX` 时的 heap scan、并行 build、图构建流程

`src/hnswutils.c`：

- 构建阶段也会复用部分 HNSW 搜索和图连接逻辑

### 验证指标

```text
CREATE INDEX 总耗时
不同数据规模下构建耗时
maintenance_work_mem 使用情况
构建阶段 CPU / I/O 占比
索引构建后 Recall@10
```

### 必要性

中。

AI Infra 场景中，离线构建向量索引也很重要，但相比在线查询路径，优先级略低。

### 可行性

中。

原因：

- PostgreSQL 已经对表扫描和 Buffer Pool 有自己的策略
- 盲目预取不一定提升性能
- 需要先 benchmark 定位真正瓶颈

## Phase 4：并行 build 锁粒度优化

### 目标

第四阶段研究 HNSW 并行构建阶段的锁竞争问题。pgvector 的 HNSW build 支持并行 worker，但图连接阶段涉及共享图结构更新，可能存在锁竞争。

目标是在保证索引正确性的前提下，降低并行 build 中的锁冲突，提高大规模索引构建吞吐。

### 可能方向

```text
1. 统计并行 build 中锁等待位置
2. 分析 HnswInsertElement / 图连接阶段的锁范围
3. 评估 page-level lock、element LWLock、entry lock 的竞争情况
4. 在明确瓶颈后，再考虑更细粒度的锁策略
```

### 主要修改文件

```text
src/hnswbuild.c
src/hnswinsert.c
src/hnswutils.c
src/hnsw.h
```

### 文件作用

`src/hnswbuild.c`：

- 并行 build 入口和 worker 协作

`src/hnswinsert.c`：

- 单个元素插入 HNSW 图
- 构建期和增量插入都会涉及图连接逻辑

`src/hnswutils.c`：

- 邻居选择、连接更新、图搜索等公共逻辑

`src/hnsw.h`：

- HNSW 元素结构、锁字段、共享构建状态定义

### 验证指标

```text
并行 CREATE INDEX 构建耗时
不同 worker 数下的加速比
锁等待时间
构建后 Recall@10
VACUUM / INSERT / SCAN 回归测试
```

### 必要性

中。

这个方向对大规模离线建库有意义，但实现风险高，适合作为后期深入优化。

### 可行性

中低。

原因：

- 涉及 HNSW 图结构正确性
- 涉及 PostgreSQL buffer lock / LWLock / WAL 交互
- 需要大量并发测试
- 一旦处理不好，可能造成索引损坏或死锁

## 当前推荐实现顺序

```text
第一优先级：Phase 1
第二优先级：Phase 2
第三优先级：Phase 3
第四优先级：Phase 4
```

也就是说，当前最应该先做的是：

```text
HNSW 查询路径 GUC + neighbor prefetch + hot layer 策略
```

原因：

- 最贴近 AI Agent / RAG 在线检索热点
- 改动范围可控
- 不影响磁盘格式
- 不触碰 VACUUM 正确性
- 可以通过现有 `test/hot_cold` 脚手架验证

---

## 当前不纳入实现范围

以下方向暂时不纳入当前路线：

```text
邻居距离 float16 压缩
复杂自建 hot cache
VACUUM 路径改动
```

原因：

- 当前 HNSW 磁盘邻居列表主要存 `ItemPointerData`，不是 `ItemPointerData + distance float`
- PostgreSQL 已经有 Buffer Pool，自建缓存容易引入一致性和生命周期问题
- VACUUM 路径关系到索引正确性，pgvector 0.8.3 / 0.8.4 刚修过相关问题，不适合作为第一阶段实验入口
