## 简历正文版本（150-200 字，适合放简历"项目经历"）

**pgvector HNSW 向量索引查询与构建优化**（2024.08，个人项目）

针对 RAG 在线检索场景，对 PostgreSQL pgvector 的 HNSW 向量索引做系统性优化：

1. **Phase 1 - Buffer Pool 预取**：在 HNSW 邻居加载前发起 `PrefetchBuffer` 异步 I/O，将串行随机读转为并发预取。200k 行数据集下 p99 延迟从 48ms 降至 21ms（-55.9%），avg 降低 32.8%，Recall@10 完全一致。
   
2. **Phase 2 - 半动态 ef_search**：在 iterative scan 时按倍率递增 batch_size，解决 WHERE 过滤场景召回不足。带过滤查询延迟降低 21.8%。

3. **Phase 3/4 - 构建期观测**：通过 `pg_stat_io` 量化构建瓶颈在 CPU 距离计算而非 I/O，避免盲目优化；并行加速比达 2.13x（2 workers）。

**技术要点**：仅 ~100 行核心代码，零磁盘格式改动，6 个可灰度 GUC，完整 benchmark 脚手架。代码已开源至 GitHub，含完整技术报告。

**技能体现**：C 语言、PostgreSQL 内核、向量检索算法（HNSW）、系统性能优化、实验设计与 benchmark。

## 面试交流版（口语化，2-3 分钟）

**背景**：我在学习 RAG 系统时发现 pgvector 的 HNSW 索引在大数据集下 p99 延迟比较高，影响在线检索体验，就想优化一下。

**Phase 1 - 核心优化**：HNSW 查询时要逐个访问邻居节点，这些节点分散在不同 index page 上，容易触发 buffer miss 同步等待。我在 `HnswSearchLayer` 里加了 `PrefetchBuffer`，提前把即将访问的邻居页面发起异步 I/O，后续访问时大概率已经在 buffer pool 里了。这样把串行 I/O 转成了并发预取，200k 行数据下 p99 从 48 毫秒降到 21 毫秒，降了 56%。关键是召回率完全不变，因为预取只是 I/O 提示，不改变搜索结果。

**Phase 2**：我还发现如果查询带 WHERE 过滤，`ef_search` 固定值容易不够用。pgvector 有个 iterative scan 机制会自动 resume，我就在每次 resume 时按 2 倍递增 batch size，让搜索逐步扩展。这在过滤场景下又降了 22% 延迟。

**Phase 3/4**：我担心构建期也有 I/O 瓶颈，就写了个观测脚本抓 `pg_stat_io`，发现其实瓶颈是 CPU 的距离计算，`reads` 只有 2 次，所以没必要动 build 代码。另外测了并行构建，2 个 worker 就能到 2.13 倍加速，再多收益递减，说明锁竞争不是主要问题。

**工程价值**：整个优化只改了 ~100 行 C 代码，没动磁盘格式，所有功能都可以通过 GUC 灰度开关，随时回退。我还写了完整的 benchmark 脚手架和技术报告，代码已经放 GitHub 了。

**收获**：深入理解了 PostgreSQL Buffer Pool 和 Index AM 接口，学会了怎么在 PostgreSQL 这种成熟系统里做性能优化——观测先行、数据驱动、小步迭代、灰度可控。

## LinkedIn 项目描述（英文，150 词）

**PostgreSQL pgvector HNSW Index Optimization for AI Infra**

Systematically optimized pgvector's HNSW vector index for RAG online retrieval scenarios:

- **Phase 1 - Buffer Pool Prefetch**: Injected `PrefetchBuffer()` before neighbor loading to convert serial random I/O into concurrent prefetch. On 200k vectors (128-dim), reduced p99 latency by 55.9% (48ms → 21ms) and avg by 32.8%, while maintaining Recall@10 unchanged.

- **Phase 2 - Semi-Dynamic ef_search**: Implemented batch escalation during iterative scans to handle WHERE-filtered queries, reducing execution time by 21.8%.

- **Phase 3/4 - Build Profiling**: Quantified build-time bottleneck as CPU-bound (distance computation) rather than I/O via `pg_stat_io`; parallel build achieves 2.13x speedup with 2 workers.

**Technical Highlights**: ~100 LOC core changes, zero disk format modification, 6 gradual-rollout GUCs, comprehensive benchmark scaffolding. Open-sourced with full technical report.

**Skills**: C, PostgreSQL Internals, Vector Search (HNSW), Performance Optimization, Benchmarking.
